Native macOS architecture

Evidence, interpretation, outcomes.

Arco separates the durable meeting record from optional Agent interpretation. The UI, Rust control plane, audio workers, transcription providers, and Codex or Claude sessions each have a narrow boundary.

The three-layer model

  1. Evidence: a timestamped, speaker-labeled transcript that remains useful even when Agent features are disabled.
  2. Interpretation: optional Codex or Claude answers, generated meeting titles, and end-of-meeting summaries with explicit context boundaries.
  3. Outcomes: only the notes and Agent answers the user explicitly chooses to keep.

This prevents a plausible model response from silently becoming a fact, decision, or task.

Native interface, Rust authority

Arco is a native macOS application. SwiftUI renders the main workspace, History, Settings, onboarding, recording HUD, and global Agent window. AppKit owns native window and panel lifecycle, global shortcuts, and system pickers.

An in-process Rust static library owns meeting state, capture policy, storage, credentials, provider routing, and Agent lifecycle. Swift and Rust communicate through a narrow C ABI with versioned JSON commands and events. There is no browser runtime inside the app.

Isolated real-time and model work

Audio capture, cloud transcription streams, and local speech models run in app-managed worker processes instead of the UI process. This keeps model memory, network failures, and audio lifecycle failures from directly taking down the main interface.

  • ScreenCaptureKit captures system audio.
  • AVAudioEngine captures the selected room microphone.
  • The recorder outputs two source lanes for online, in-person, or hybrid meetings.
  • Cloud and on-device transcription workers publish readiness before Arco reports that recording has started.
  • Stopping or failing a meeting targets only the exact process tree Arco created.

Streaming transcription and speaker separation

Speech recognition and speaker separation are independently selectable roles. Arco can fuse a provider that supplies both, or combine one ASR provider with another streaming diarization provider.

Supported ASR paths include Deepgram, Doubao Speech, ElevenLabs Scribe v2 Realtime, on-device Nemotron, and on-device Whisper. Supported speaker-separation paths include Deepgram, Doubao Speech, and on-device Sortformer, Pyannote + WeSpeaker, and LS-EEND.

Only finalized speech becomes durable transcript evidence. Arco does not wait until the meeting ends to run a second batch pass and overwrite the transcript.

Speaker labels do not invent identity

The identity key is the combination of source channel and speaker slot. System audio produces labels such as Remote 1; the room microphone produces labels such as In room 1. A single room microphone may contain multiple people, so Arco never assumes that microphone audio is the user.

Exact Agent session continuity

Each meeting, provider, context scope, and selected workspace owns an exact native Codex or Claude session binding. Follow-up questions resume that provider-generated ID. Arco never asks the CLI to resume whichever conversation happened most recently.

The provider's native conversation remains the continuity source. Arco stores the meeting binding, a display cache, and saved-note metadata locally. Background title and summary generation uses a separate session so those prompts never appear as user questions in Ask Arco.

Portable storage

Transcripts and notes are Markdown. Atomic JSON sidecars preserve Agent session bindings, cached answer cards, generated meeting output, and saved-note state without rewriting legacy transcript files. The active meeting and the meeting currently being reviewed remain separate state, so opening History cannot redirect an active recording.
